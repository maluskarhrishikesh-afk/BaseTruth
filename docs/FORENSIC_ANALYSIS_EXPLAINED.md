# BaseTruth Forensic Analysis — How It Works, How Accurate It Is, and What We Can Improve

> Written in plain English. No computer science degree required.

---

## The Big Picture

When someone uploads a document to BaseTruth, we run it through two separate forensic engines depending on what kind of file it is:

- **Image engine** — for photos (JPG, PNG, etc.) and scanned-image PDFs  
- **PDF engine** — for digitally-created PDFs (payslips generated by payroll software, offer letters from Word, bank statements from banking portals, etc.)

Both engines use **11 independent checks** ("layers"). Each layer looks for a different type of evidence of tampering. No single layer is ever decisive on its own — the final verdict is based on how many layers fire together and how strong each signal is. This multi-layer voting approach is deliberately chosen so that one false alarm from one layer does not cause an incorrect verdict.

At the end, all findings are added up into a **Forgery Score** from 0 to 100:

| Score | Verdict |
|---|---|
| 0 – 14 | **ORIGINAL** — no meaningful evidence of tampering |
| 15 – 29 | **UNCERTAIN** — some minor signals, possibly innocent (e.g. routine re-save) |
| 30 – 54 | **LIKELY TAMPERED** — multiple independent signals align; manual review needed |
| 55 – 100 | **TAMPERED** — strong, multi-layer evidence of deliberate alteration |

## Engine 1: Image Forensics (scanned documents and photos)

Used for: JPG, PNG, TIFF, BMP, WebP, and PDFs that are scanned images.

---

### Layer 1 — Error Level Analysis (ELA)

**What it detects:** Areas that were pasted onto an image or typed over.

**How it works:**  
Every JPEG image loses a little quality when saved. If you paste new content onto an old image and save it again, the pasted area has been through fewer compression cycles than the rest of the image. We re-save the image at a known quality level (75%), subtract it from the original pixel-by-pixel, and measure how bright each region glows in the resulting "error heatmap." The image is divided into 32×32 pixel tiles. If more than 5% of tiles glow brighter than 2.5× the average, that is a red flag.

**Threshold:** suspicious_block_ratio > 5% → flags as SUSPICIOUS. Adds 25 points to the forgery score.

**Limitation:** Heavily compressed mobile-phone scans can produce high ELA naturally even without tampering. The threshold may need tuning for very low-quality originals.

---

### Layer 2 — Metadata / EXIF Analysis

**What it detects:** Evidence that the image was opened and edited in a photo editor.

**How it works:**  
Every digital photo taken by a real camera contains hidden information tags (EXIF data) recording: which camera took it, when the shutter was pressed (DateTimeOriginal), and which software last touched it. We check for:
- Known editing tools in the Software tag (Photoshop, GIMP, Canva, Paint, Snapseed, etc.)
- Missing camera Make/Model (the photo was not taken by a camera — it came from a screen or a generator)
- Missing DateTimeOriginal (stripped by an editor)
- DateTimeOriginal different from ImageDateTime (the image was edited and re-saved after the original shot)
- Completely absent EXIF (all tags stripped — common when editing tools re-export)

**Scoring:** Each suspicious flag adds 10 points to the forgery score.

**Limitation:** Some legitimate scanning apps also strip or partially overwrite EXIF. This means a scanned document submitted via a phone scanner app may get false flags on the metadata layer. We mitigate this by requiring multiple layers to fire before escalating to TAMPERED.

---

### Layer 3 — File Entropy (Data Randomness)

**What it detects:** Files that have been repeatedly re-saved or re-compressed.

**How it works:**  
Shannon entropy is a measure of how "random" the raw bytes of a file are. A freshly created, unedited JPEG photo has entropy between 7.8 and 8.0 bits per byte because JPEG compression produces near-random byte patterns. Files that have been repeatedly edited and re-saved lose some natural randomness, pushing the score below 7.8.

**Threshold:** entropy < 7.8 → SUSPICIOUS. Used as a supporting signal; does not add points on its own for image files.

**Limitation:** This is a weak standalone signal. It is most useful when combined with other evidence. Low entropy alone is not conclusive.

---

### Layer 4 — Noise Residual Analysis

**What it detects:** Images assembled by patching together content from different source photos.

**How it works:**  
Every real camera sensor adds a faint, invisible "grain" pattern to every photo. Because this grain comes from the hardware, it should look statistically the same everywhere in the image. If someone pastes content from a different photo onto this one, the noise pattern at the boundary changes abruptly — like a fingerprint mismatch at a join line.

We blur the image with a Gaussian filter to remove all real detail, leaving only the noise. The image is divided into 64×64 pixel tiles. We compute the Coefficient of Variation (CV = standard deviation ÷ mean) for each tile. If more than 10% of tiles have a CV more than 2× the global average, noise is inconsistent.

**Threshold:** hotspot_tile_ratio > 10% → adds 15 points.

---

### Layer 5 — DCT Double-Compression Detection (JPEG only)

**What it detects:** JPEG images that were opened, edited, and re-saved as JPEG.

**How it works:**  
JPEG compression works by dividing the image into 8×8 pixel blocks and running a mathematical frequency transform (Discrete Cosine Transform, or DCT) on each block. When a JPEG is edited and re-saved as JPEG, the block grid of the original save interferes with the block grid of the new save. This leaves a characteristic "comb" pattern in the histogram of DCT AC coefficients — a repeating sequence of local minima and maxima that should not exist in a single-compressed original. We measure the ratio of local minima to local maxima (comb_ratio). A ratio > 1.3 indicates double-compression.

**Threshold:** comb_ratio > 1.3 → adds 20 points. Only applies to JPEG. PNG is lossless and skips this layer.

---

### Layer 6 — Clone / Copy-Move Detection

**What it detects:** Areas within the same image that were cloned to cover up content.

**How it works:**  
A clone stamp is a photo-editing tool that copies a patch of the image onto another area — for example, copying a clean background texture over a signature, date, or salary number to erase it. We use the SIFT (Scale-Invariant Feature Transform) algorithm to find up to 3,000 distinctive visual keypoints in the image. We then match every keypoint against every other keypoint. If two keypoints are very visually similar (distance < 120) but are physically far apart in the image (> 50 pixels), they were likely cloned from each other. If more than 25% of all keypoints have such a clone match, we flag it.

**Threshold:** clone_ratio > 0.25 → adds 12 points.

**Limitation:** Only catches cloning within the same image. It will not detect content pasted from a completely different document.

---

### Layer 7 — Color Anomaly Detection

**What it detects:** Pixels whose colour does not fit the rest of the image's natural palette.

**How it works:**  
Real photographs have a dominant colour palette (skin tones, background colours, paper white, etc.). A digital paste or colour-fill often introduces colours that don't match anything else in the image — like a perfectly bright-blue rectangle on a document that has no blue content anywhere else.

We convert the image to HSV (Hue, Saturation, Value) colour space. We build a histogram of hue values for all non-dark, non-grey foreground pixels. We find the top 3 dominant hue bins and define a tolerance of ±10 degrees around each. Any pixel that is vibrant (Saturation > 60) but falls outside the dominant palette is classified as a colour anomaly. We then group anomaly pixels into blobs using connected-component analysis. Large blobs (area > 2,000 pixels) almost always indicate a paste or annotation.

**Threshold:** anomaly_ratio > 1% or largest blob > 2,000 px → adds 35 points. anomaly_ratio > 0.3% → adds 18 points.

**Known false-positive case:** Blue watermarks, official stamps, and background colours that are intentionally non-dominant (e.g. the blue background in a passport photo) will be flagged by this layer. The size-gating (> 2,000 px) mitigates small incidental anomalies but large blue backgrounds still fire.

---

### Layer 8 — Edge Discontinuity / Density Analysis

**What it detects:** Unnaturally sharp edges caused by digital drawing, pasting, or overlays.

**How it works:**  
Natural photographs have soft, camera-blurred edges. When someone pastes a region onto an existing image or draws a digital box, the resulting edge is perfectly straight and laser-sharp — unlike anything a camera produces. We use the Canny edge detector to find edges, divide the result into 32×32 tiles, and flag tiles with an edge density more than 3× the average.

**Threshold:** high_density_tile_ratio > 6% → adds 12 points.

---

### Layer 9 — Saturation Anomaly Detection

**What it detects:** Localised colour filters, bright highlights, or vivid annotations applied to one area.

**How it works:**  
Applying a bright-colour overlay (highlighting, a coloured stamp, a vivid digital annotation) to just one part of a document makes that region far more saturated than the rest of the image. We divide the image into 32×32 tiles, compute the mean saturation (in the HSV S channel) for each tile, and flag tiles whose saturation is more than 3× the global average.

**Threshold:** high_saturation_tile_ratio > 2% → adds 8 points.

---

### Layer 10 — Font Consistency Analysis

**What it detects:** Text that was typed over the original document — e.g. a salary number changed in an image editor, or cut-and-pasted text that is vertically misaligned.

**How it works:**  
This layer only applies to documents with text (it skips photos and non-text documents with fewer than 20 detected characters). When someone opens a document image and types new text, the new text usually differs from the original in four ways: stroke width (letter thickness), character height, sharpness (different anti-aliasing), and baseline alignment. We extract all text blobs using adaptive thresholding. For each blob we measure stroke width, height, sharpness, and calculate its baseline (`y + height`). We cluster characters into horizontal lines and check the standard deviation of baselines. Cut-and-paste text often produces a "baseline jitter" > 1.5 pixels. We compute outlier ratios and look for spatially-clustered groups of outliers. A cluster of outlier characters is strong evidence of text replacement.

**Threshold:** (stroke_cv > 0.40 AND at least 1 anomaly region) OR (≥ 2 anomaly regions) OR (sharpness_outlier_ratio > 25% AND ≥ 1 region) OR (high baseline jitter) → adds 15–20 points.

---

### Layer 11 — AI Generative Model Detection

**What it detects:** Images produced by AI image generators (Midjourney, Stable Diffusion, DALL-E, etc.).

**How it works:**  
AI image generators are based on mathematical structures using grid convolutions. These structures leave a faint, invisible "checkerboard" or "frequency spike" pattern in the image's frequency domain — detectable via 2-D Fast Fourier Transform (FFT). We convert the image to greyscale, apply an FFT, shift the zero-frequency component to the centre, and measure the peak-to-background ratio of high-frequency spikes. A spike_ratio > 3.0 indicates unnatural periodicity consistent with AI generation.

**Threshold:** spike_ratio > 3.5 → adds 25 points. spike_ratio > 3.0 → adds 15 points.

**Limitation:** This method catches diffusion-model and older GAN-based artifacts, but newer GAN architectures (e.g. StyleGAN3) produce faces without leaving visible Fourier signatures. A dedicated face-authenticity model (e.g. UniFAD) would close this gap.

## Engine 2: PDF Forensics (digitally-created PDFs)

Used for: PDFs generated by software (payroll systems, Word, Google Docs, banking portals). These PDFs have embedded text that can be extracted directly.

---

### Layer 1 — Incremental Update Detection

**What it detects:** PDFs that were modified after they were originally generated.

**How it works:**  
A normally generated PDF has exactly one end-of-file marker (`%%EOF`) at the bottom. When someone opens a PDF in an editor, changes a number (e.g. alters a salary figure), and saves it, the editing tool appends the changed data before a second `%%EOF` instead of rewriting the whole file. This is called an "incremental update." Counting `%%EOF` markers tells us exactly how many times the file was saved after original creation. Any count > 1 means the file was modified post-creation.

**Scoring:** Each incremental update adds 30 points (capped at 45). This is the single strongest PDF tampering signal.

---

### Layer 2 — Metadata Analysis

**What it detects:** PDF editing tools in the document's information card, and suspicious date patterns.

**How it works:**  
Every PDF carries a hidden information card listing: Creator (the application that made the source document, e.g. "Microsoft Word"), Producer (the PDF library that rendered it, e.g. "Microsoft Word for Windows"), CreationDate, and ModDate. We check:
- Whether any known PDF editing/manipulation tools appear in the Creator or Producer field (ilovepdf, Smallpdf, Sejda, PDFescape, Foxit, Nitro, etc.)
- Whether the ModDate is later than the CreationDate by more than 60 seconds (genuine edit)
- Whether the metadata is completely absent (stripped by an online tool)
- Whether the CreationDate is missing while other fields are present (partial stripping)

**Scoring:** Editing tool found → 20 points. Date gap or absent metadata → 10 points each.

---

### Layer 3 — Font Consistency Analysis

**What it detects:** Text typed in a different tool than the original document.

**How it works:**  
A genuine payslip generated in one pass by payroll software uses the same font family on every page. If someone opens the PDF in an editor and types a new number, that number will typically be in a different font (or a different embedding style) than the surrounding text. We catalogue every font on every page and check for: fonts that are not embedded (may render differently elsewhere), fonts that appear only on later pages but not on page 1 (added after the fact), and an unusually high number of distinct font families (common in paste/merge operations).

**Scoring:** Post-creation font insertion → 15 points. Other font anomalies → 10 points each.

---

### Layer 4 — Invisible / Hidden Text Detection (Shadow Attacks)

**What it detects:** Text that exists in the PDF file but is visually hidden, or "Shadow Attack" text layered perfectly over other text.

**How it works:**  
Forgers often hide data inside a PDF by placing text with its colour set to white, setting the font size near-zero (0.001 pt), or using a "Shadow Attack" where a visual mask (or new text) perfectly overlaps the original text, obscuring it while both strings remain in the file. We scan every text span using PyMuPDF, checking colour values (all R, G, B channels > 240 = near-white), font size (< 0.5 pt = invisible), and bounding box Intersections. If two different text blocks share > 80% overlapping coordinate space, it flags as a shadow edit overlay.

**Scoring:** Any hidden, zero-size, or shadow text found → 25 points. This is a high-confidence signal; legitimate documents should have zero hidden/occluded text masks.

---

### Layer 5 — Suspicious Object Detection

**What it detects:** JavaScript, embedded files, auto-run actions, and XFA dynamic forms.

**How it works:**  
A genuine payslip is a dead-simple PDF: text, a logo image, maybe a table. It should contain zero JavaScript, no embedded executables, and no form actions that fire automatically. We scan the raw bytes of the PDF for: `/JS` or `/JavaScript` (embedded scripts), `/EmbeddedFile` (attached files), `/OpenAction` (runs automatically on open), `/AA` (additional actions / form triggers), `/XFA` (dynamic XML-based form layer that can display different values from the static text layer), and `/Launch` (external execution triggers).

**Scoring:** JavaScript → 40 points. Embedded files → 20 points. OpenAction → 15 points. XFA form → 12 points.

---

### Layer 6 — Content Consistency Analysis

**What it detects:** Documents assembled from multiple sources, or with blank pages hiding original content.

**How it works:**  
A payslip generated in one pass will have: consistent page dimensions throughout (all A4 or all Letter), no completely blank pages, and a fairly uniform text density per page. We check for: more than 2 distinct page sizes, blank pages (fewer than 5 characters), and pages whose character count is more than 3 standard deviations away from the document average.

**Scoring:** Each suspicious flag adds 12 points.

---

### Layer 7 — Digital Signature Check

**What it detects:** PDFs modified after they were digitally signed.

**How it works:**  
A digital signature in a PDF covers a specific byte range of the file at the moment of signing (ByteRange). Any edit made after signing changes bytes outside this range, creating an "uncovered" gap at the end of the file. We check for the presence of a signature field, extract all ByteRange records, and calculate how many bytes after the last signed region are uncovered. More than 64 uncovered bytes after the signed region is a critical finding: the document was altered after signing.

**Scoring:** Signature with coverage gap → 35 points.

---

### Layer 8 — Page Render ELA + Noise

**What it detects:** Pixel-level tampering on digitally-created PDFs (same idea as Image Layer 1 and 4).

**How it works:**  
We rasterize page 1 of the PDF to a high-quality JPEG image at 150 DPI, then run the same ELA analysis (Layer 1 from the image engine) and noise residual analysis (Layer 4 from the image engine) on the resulting image. This catches cases where someone edited the visual appearance of the PDF at the pixel level rather than at the text-object level.

**Scoring:** ELA suspicious_block_ratio > 5% → 20 points. > 2% → 10 points. Noise hotspot > 10% → 15 points.

---

### Layer 9 — Embedded Image Noise Analysis

**What it detects:** Logos, stamps, or signature images that were swapped or pasted.

**How it works:**  
Many HR documents contain embedded images (company logo, signature, official stamp). We extract all embedded images from the PDF, identify the largest one (most likely to contain forged content), and run the noise residual analysis on it. If the noise pattern within the embedded image has more than 12% hotspot tiles, it suggests the image was composited from different sources.

**Scoring:** Embedded image noise hotspot > 12% → 10 points.

---

### Layer 10 — File Entropy

**What it detects:** Repeatedly re-compressed or abnormally structured PDF files.

**How it works:**  
Shannon entropy of the raw PDF bytes. A normal PDF full of compressed streams scores 7.5–8.0 bits per byte. PDFs with unusually low entropy (< 7.0) may have been re-exported through tools that added large uncompressed sections or stripped compression. This is a supporting signal only.

**Scoring:** entropy < 7.0 → 8 points.

---

### Layer 11 — Object / Cross-Reference Integrity

**What it detects:** Inconsistencies in the PDF's internal object table that suggest objects were added or modified outside the normal save process.

**How it works:**  
A PDF is made of numbered objects (fonts, images, page content streams, etc.) all listed in a cross-reference table (xref). The PDF header declares how many objects exist. Using pikepdf, we count all actual objects in the file and compare to the declared count. A mismatch of more than 5 objects suggests the xref table was not properly updated after modification. We also flag compressed ObjStm streams (which pack multiple objects inside a single stream in a way that basic text scanners cannot read).

**Scoring:** Object count mismatch → 20 points. ObjStm found → 8 points.

## How Accurate Are We?

This is an honest self-assessment of the current engine.

### What the engine is good at

| Scenario | Detection reliability |
|---|---|
| PDF edited with an online tool (ilovepdf, Smallpdf, etc.) | **Very high** — incremental updates + metadata editing tool both fire |
| JPEG photo edited in Photoshop / GIMP | **High** — ELA + metadata software tag + DCT usually all fire |
| Salary number typed over an image-based payslip | **Medium-high** — font consistency layer catches stroke-width change |
| Completely AI-generated identity photo | **Medium** — FFT spike ratio catches diffusion-model grid artifacts |
| Invisible white text hidden in a PDF | **Very high** — explicit byte-level check, near-zero false positive rate |
| JavaScript or XFA form in a payslip PDF | **Very high** — binary pattern scan, cannot be hidden |
| Digital signature broken by post-signing edit | **Very high** — ByteRange math is cryptographic |
| Copy-move within the same image | **Medium** — SIFT clone detection catches obvious clone stamps |

### Where we are weaker

| Scenario | Current reliability |
|---|---|
| Minor single-field text edits in a scanned image (e.g. one digit changed in a salary row) | **Low-medium** — font layer may miss subtle changes if the forger matched the font carefully |
| Deepfake or StyleGAN3 face in a photo | **Low** — FFT approach misses new GAN architectures that don't leave frequency artifacts |
| Content pasted from a different document into the same image | **Low** — clone detection only finds self-matches within the same image |
| Professionally edited PDF (preserving original metadata, re-embedding fonts correctly) | **Low-medium** — a skilled forger who knows about incremental updates can avoid most PDF flags |
| Blue backgrounds or official stamps on photos | **Known false positive** — colour anomaly layer fires on large dominant non-palette regions |
| Scanned documents submitted via mobile scanning apps | **Known false positive** — metadata and entropy layers may fire on innocent re-saves |

### Overall accuracy ballpark

In testing against a mix of known-tampered and known-authentic documents, the multi-layer engine achieves roughly:
- **True positive rate (catching tampering when present): ~80–85%** for obvious edits (salary changes, date changes using common tools)
- **False positive rate (flagging a clean document as suspicious): ~10–15%** primarily driven by the colour anomaly and metadata layers firing on mobile-scanned documents

These numbers are not validated on a large labelled benchmark dataset — they are based on the internal test cases in the `artifacts/` folder. A proper accuracy study against a diverse, independent dataset is one of the recommended improvements below.

## Improvement Areas — Ordered by Impact

The following are concrete improvements ranked by how much they would move the accuracy needle. None of these are implemented yet.

---

### 1. Add a Trained Classifier on Top of the 11-Layer Features (Highest Impact)

**Current situation:** The 11 layers produce signals and the scoring model applies fixed, manually-tuned weights.

**The problem:** The weights were set by intuition and the test cases in the `artifacts/` folder. They are not calibrated against a real, diverse, labelled dataset. A mobile-scanned clean document may score 40 points (triggering LIKELY TAMPERED) purely because the metadata and colour anomaly layers fire simultaneously.

**Improvement:** Train a binary classifier (logistic regression or a shallow gradient boosted tree) on the 11-layer output features using a labelled dataset of tampered vs. authentic documents. The classifier will learn the correct interaction weights between layers — for example, it will learn that "metadata flags alone on a JPEG from a mobile scanner" is not the same risk as "metadata flags + ELA flags + DCT flags all firing together."

**Expected gain:** Reduce false positive rate from ~15% to ~5%, and improve true positive rate by ~10 percentage points on subtle edits.

---

### 2. ELA with Adaptive Threshold Per Document Type (High Impact)

**Current situation:** The ELA suspicious-block threshold is fixed at 5% globally.

**The problem:** Heavily compressed originals (WhatsApp-shared documents, heavily-scanned payslips) produce high ELA naturally. The fixed 5% threshold fires on these clean documents.

**Improvement:** Use a reference-based ELA threshold. For each document type, maintain a calibrated baseline ELA distribution (e.g. "a clean payslip scan typically has ELA suspicious_block_ratio of 2–4%"). Threshold at mean + 2σ for each document type rather than at a global 5%.

---

### 3. GAN / Deepfake Face Detection (High Impact for Identity Documents)

**Current situation:** Layer 11 (FFT spike ratio) only catches diffusion-model artifacts. It misses modern GAN-generated faces.

**The problem:** A forged PAN card or Aadhaar with a GAN-generated face will pass Layer 11 cleanly.

**Improvement:** Integrate a dedicated face-authenticity detector such as:
- **UniFAD** (Universal Face Anti-spoofing Detector) — open source, runs on CPU
- **GragnanielloGAN** — specifically calibrated for document-grade deepfakes
Run it on any image that contains a detected face (from the InsightFace/MediaPipe face detector already present in the codebase).

---

### 4. Localized ELA with Heatmap Overlay — **DONE**

**Status:** Implemented and live in the Forensic Scan screen.

Two views are available when a scan completes on an image document:
- **ELA Map** (default): the raw ELA signal amplified ×10 with INFERNO colour scale applied. No original image mixed in. Black/purple = clean; orange/yellow = tampered.
- **Overlay**: the original document with heatmap colour only on the top 25% most suspicious pixels. Clean regions stay 100% original. Useful for locating the tampered area within the document layout.

See the new section *"The Forensic Heatmap — How to Read It"* below for a full reading guide.

---

### 5. Cross-Document Consistency for Multiple Payslips (Medium Impact)

**Current situation:** Each document is analysed in isolation.

**The problem:** A sophisticated forger might change the salary on one payslip only slightly (e.g. from ₹45,000 to ₹55,000) — just enough to qualify for a larger loan. Isolated single-document analysis may not catch this because every individual layer is borderline.

**Improvement:** When multiple payslips from the same entity are available (e.g. the last 6 months), compare salary progression, employer name consistency, font fingerprint consistency, and file-entropy trends across the set. An anomalous jump in one month while everything else is stable is a strong signal. The Bulk Scan pipeline already runs these documents together — the cross-document fraud signals need to be surfaced more prominently in the scoring.

---

### 6. Content-Aware Color Anomaly (Medium Impact — Reduces False Positives)

**Current situation:** Layer 7 (colour anomaly) flags any large region whose hue is not in the top-3 dominant hues.

**The problem:** Blue backgrounds in passport photos, official blue stamps, and coloured tables are legitimate and will fire this layer as a false positive.

**Improvement:** Apply the colour anomaly check only to regions expected to be monochrome (white paper background, printed black text areas). Use the document type to define expected colour regions. For a "passport" type document, the blue background zone is expected and should be excluded from the anomaly check. For a "payslip" document, any non-black non-white region in the salary table area is unexpected and should be scored more heavily.

---

### 7. Named Entity Consistency Check (Medium Impact)

**Current situation:** Field extraction (Gemma AI) and forensic analysis run independently. Extracted fields are not used in the forensic scoring.

**The problem:** A payslip where the employee name on the header is "Ravi Kumar" but the PF deduction slip embedded in the same PDF is in the name "Ravi Sharma" is suspicious — but neither the forensic engine nor the extraction engine currently raises this cross-field inconsistency.

**Improvement:** After extraction, run a named entity consistency pass: verify that the employee name, company name, PAN number, and month/year are internally consistent across all sections of the same document. Raise a forensic signal for mismatches.

---

### 8. Steganography Detection (Low-Medium Impact, Niche)

**Current situation:** No check for data hidden inside the image pixels themselves.

**The problem:** Advanced forgers can hide modified metadata or alternate values inside the least-significant bits (LSB) of image pixels — invisible to the human eye but detectable statistically.

**Improvement:** Add an LSB analysis layer: check the statistical distribution of the least-significant bits across the image. A natural photo has near-random LSBs. Modified content embedded via LSB steganography produces slightly non-random distributions. Libraries like `stegano` or custom chi-square LSB analysis can detect this.

---

### 9. Validated Benchmark Dataset (Infrastructure)

**Current situation:** Accuracy claims are based on informal testing against the documents in the `artifacts/` folder.

**The problem:** The `artifacts/` folder is a small, non-diverse set dominated by documents from one person. This is not a valid basis for accuracy claims when selling to banks or insurance companies.

**Improvement:** Build a labelled benchmark dataset of at least 500 documents (50% authentic, 50% tampered with known modification types: salary change, date change, online-tool re-export, AI-generated photo, etc.). Compute precision, recall, and F1 for each verdict class. Re-tune the scoring weights against this dataset before any enterprise deployment.

## The Forensic Heatmap — How to Read It

> This section explains both views shown under the **🗺️ Forensic Heatmap** card on the Forensic Scan screen.

The heatmap only appears for image-based documents (JPG, PNG, scanned PDFs). It is not shown for digitally-created PDFs (those use the PDF engine and a different set of signals).

---

### What is ELA and why does it glow?

Every time a JPEG image is saved, it loses a tiny amount of quality. This is called JPEG compression loss. If you take an old image and paste new content onto it, the pasted area has been through fewer compression cycles than the rest of the image. When you re-save the whole thing at a controlled quality level, the pasted area responds differently — it glows brighter in the difference image.

This difference image is called the **Error Level Analysis (ELA)** map. Bright areas mean "this region did not age the way the rest of the image aged." That is the signature of a paste, a copy-move, or typed-over text.

---

### View 1: ELA Map (default)

This is the **primary forensic evidence view**. No original image is mixed in — you are seeing pure signal.

**The INFERNO colour scale reads like a thermometer:**

| Colour you see | What it means |
|---|---|
| Black / very dark purple | ELA near zero — completely clean, no re-compression anomaly |
| Purple | Low ELA — normal JPEG edge variation at high-contrast text boundaries |
| Blue-purple | Moderate ELA — worth watching but usually natural |
| Orange | High ELA — region shows clear re-compression history difference |
| Bright orange / yellow | Maximum ELA — very strong tampering signal |

**How to read it in practice:**

1. Look at the overall brightness of the map. A clean document is almost entirely black/dark purple with no bright patches.
2. Look for a solid bright region that does not follow the text or print pattern. Natural JPEG variation appears as speckled noise at text edges. Pasted content appears as a solid rectangle or uniform block of brightness — because the entire pasted region was compressed once together, creating a uniform ELA level.
3. Ignore faint purple at the edges of letters and ruled lines — this is normal JPEG DCT block ringing.

**Real example tested:**
A marksheet where the marks row was digitally edited ("04/2026" pasted over the original marks): the ELA Map shows the rest of the document as near-black (ELA ~ 1.3 average), and the pasted row glows as a bright pink-magenta horizontal band (ELA ~ 24, maximum 41). Nothing else in the document reaches that brightness. The tampered row stands out unambiguously.

---

### View 2: Overlay

This view shows the **original document with colour only on the top 25% most suspicious pixels**. Clean areas appear exactly as the uploaded document. Suspicious areas receive an INFERNO colour tint (same scale as the ELA Map).

The Overlay is useful when you want to know *where in the document* the suspicious area sits — which row, which field, which corner. It provides spatial context that the pure ELA Map (which has no document labels visible) cannot give on its own.

**How to read it:**
- Clean background, printed text, official stamps → appear normal, no colour
- Tampered area → receives an orange/yellow colour tint visible against the document background
- Very faint colouring on a white page is expected — it means that area had moderately elevated ELA (above the 75th percentile but not extreme)
- A strongly coloured region means the ELA in that area is far above everything else in the document

---

### When the heatmap is NOT conclusive on its own

The heatmap catches paste and copy-move edits reliably. It is less conclusive in these cases:
- The edit was a text replacement where the forger carefully matched the font and JPEG quality of the original — the ELA may not be elevated enough to show a hotspot
- The image is a low-quality photo (e.g. WhatsApp-compressed) — natural JPEG variation is higher, so the tampered area may not stand out as sharply
- The document is a PNG (lossless) — ELA is still computed but the initial JPEG conversion adds baseline noise

In these cases, use the ELA Map as supporting evidence alongside the other forensic layers (font consistency, noise residual, DCT double-compression) rather than as the sole signal.

## SHAP Feature Contributions — What the Model is Telling You

> This section explains the **🔬 Feature Contributions** card shown on the Forensic Scan screen when the ML model ran (badge shows 🤖 ML Model).

---

### What is SHAP?

SHAP stands for **SH**apley **A**dditive ex**P**lanations. The name comes from game theory (Shapley values). In simple terms: after the XGBoost model makes its prediction, SHAP takes apart that prediction and says exactly how much each input feature contributed to the final score.

Think of it like splitting a restaurant bill fairly. Seven people ordered dinner. SHAP figures out how much each person's order added to the total bill — so you know who drove the cost up and who barely ate.

---

### What the bar chart shows

Each bar represents one of the 11 forensic features fed to the XGBoost model. The bars are sorted from most influential to least influential for this specific document.

| Bar colour | What it means |
|---|---|
| 🔴 Red bar (positive value) | This feature pushed the model toward **TAMPERED** |
| 🟢 Green bar (negative value) | This feature pushed the model toward **GENUINE** |
| Longer bar | Stronger influence on the score |
| Shorter bar | Weaker influence, near-neutral |

The numbers shown are **log-odds units** (the internal language of XGBoost). You do not need to understand the math — just look at which bars are longest and what colour they are.

---

### The 11 features explained in plain English

| Feature name | What it measures |
|---|---|
| `ela_score` | How bright the ELA map glows (high = re-compression anomaly) |
| `dct_score` | How strongly the DCT frequency pattern suggests double-compression (JPEG only) |
| `metadata_flag_count` | How many suspicious things were found in the EXIF/metadata tags |
| `clone_ratio` | What fraction of visual keypoints have suspicious copy-move matches within the same image |
| `text_alignment_score` | Whether text baselines are vertically consistent (currently always 0 — placeholder for a future text alignment detector) |
| `font_inconsistency` | How different font strokes look across the document (high = typed-over text) |
| `signature_mismatch` | Whether a signature comparison was done (-1 = not applicable for this document type) |
| `noise_hotspots` | How many tiles have noise patterns inconsistent with the rest of the image |
| `color_patch_score` | How large and vibrant the colour anomaly regions are |
| `ai_artifact_score` | Whether the FFT frequency spectrum shows AI/GAN generation artifacts |
| `compression_mismatch` | Combined signal of ELA standard deviation and DCT double-compression |

---

### Example reading

Suppose the screen shows:
- `ela_score` → long red bar (+0.82)
- `font_inconsistency` → medium red bar (+0.41)
- `metadata_flag_count` → short green bar (−0.12)
- everything else → small bars near zero

This means: the model decided this document is probably tampered primarily because the ELA signal is very high and the font looks inconsistent. The metadata actually pushed slightly in the opposite direction (metadata looked clean). The overall score is driven by the first two features.

This gives you the ability to immediately cross-check: go to the forensic layers section and look at the ELA and Font Consistency results. If both layers also report SUSPICIOUS there, that is strong convergent evidence.

---

### When SHAP is not shown

The SHAP card only appears when:
1. The ML model file (`data/ml_scorer_image.pkl`) is present and loaded
2. The ML model ran (badge shows 🤖 ML Model, not 📐 Heuristic)

If the heuristic ran instead (model file absent or prediction failed), no SHAP breakdown is available because there is no model to explain.
